# 保守の規約（AI と人の共通ルール）

このリポジトリを直すときの規約です。AI（Claude Code など）に作業させるときも、人が直すときも同じものを使います。AI 向けの入口は、リポジトリ直下の [CLAUDE.md](../../CLAUDE.md) です。

判断の考え方は [design-principles.md](design-principles.md)、具体的な直し方は [making-changes.md](making-changes.md) にあります。この文書は「必ず守ること」と「進め方」を決めます。

## 1. 適用範囲

| 作業 | この規約の扱い |
|---|---|
| 不具合の修正、仕様の変更、ジョブの追加 | 2章の不変条件と4章の進め方を守る |
| 構造の整理（リファクタリング）・設計の改善 | 上に加えて、3章の判定で「直す」となったものだけを行う |
| 文書だけの修正 | 4章の5・6を守る |

## 2. 不変条件（必ず守ること）

次のどれかに反する変更は、理由があっても行いません。変える必要があると考えたときは、変更を提案して判断を仰ぎ、決まったら設計判断の記録（[decisions](../decisions/README.md)）を追加してから行います。

| # | 不変条件 | 根拠 | 検査 |
|---|---|---|---|
| I-1 | 「土壌分析を依頼」をクリックする操作を、ページスクリプト・操作カタログ・ページポートのどこにも作らない | 依頼は担当者が結果を確認してから行う | Flow.Tests（ページポートに依頼の操作が無いこと） |
| I-2 | 画面の**意味**の変更を吸収するように直さない（名前・状態・件数が合わないときに推測で続けない） | 取り違えたまま操作する事故を防ぐ | [decisions/0001](../decisions/0001-dom-as-contract.md)、tests/js |
| I-3 | 業務上の対象は「ちょうど1つ」に決めてから操作する。候補の先頭を使わない | 同上 | tests/js |
| I-4 | ジョブのモジュールは `JobKit` 以外を読み込まない。Context に触れるのは `Ports.ps1` とジョブコマンドだけ | 依存の向き | Architecture |

| I-8 | Windows PowerShell 5.1 で動く書き方だけを使う。PowerShell のソースは UTF-8（BOM 付き）・LF、.bat は ASCII・CRLF | 本番の実行環境 | PowerShellCompatibility、SourceHygiene |

## 3. 構造の整理をするかどうかの判定

構造の整理・設計の改善を提案するときは、次の順で判定します。どこかで「しない」になったら、その変更は行いません。

1. 対象が `tools/vendor/` なら **しない**。
2. 対象がテストなら、テストを足す・強めるとき以外は **しない**。
3. 2章の不変条件に反するなら **しない**（提案して判断を仰ぐ）。
4. [design-principles.md](design-principles.md) の「分けるべき合図」（2章）、「抽象を消す条件」（5章）、「まとめる基準」（6章）の**どれかに具体的に当てはまる**ことを示せるか。示せなければ **しない**。
5. 好み・命名の微修正・「理論上はこの方がきれい」は、依頼が無ければ **しない**。

## 4. 変更の進め方

1. **読む**: 該当するジョブ・モジュールの文書と、[making-changes.md](making-changes.md) の該当する行を読む。
2. **テストから**: 変えたい振る舞いをテストに書く（または既存のテストの期待を、仕様の変更として直す）。
3. **直す**: 変わる理由に対応する1か所を直す（[design-principles.md](design-principles.md#2-責務の置き場所単一責任)）。
4. **確かめる**: テスト一式を **Windows PowerShell 5.1** で実行する（[testing.md](testing.md#1-実行する)）。ブラウザ・画面に関わる変更は、ブラウザスクリプトのテストと、必要なら E2E も実行する。
5. **文書を直す**: 変えたものに対応する文書の「この文書を更新するとき」を見て、同じ変更で直す。
6. **記録する**: 設計の判断を変えたときは、[decisions](../decisions/README.md) に新しい記録を追加する（古い記録は書き換えず「置き換え」にする）。

文書・テスト・コードが食い違っていたときの扱いは、[docs/README.md](../README.md#文書を保守する約束) の「正本」の規則に従います。

## 5. 提案・報告の形（AI 向け）

構造の整理や設計の変更を提案するときは、次の形で書きます。「直す」ものが無ければ、改修の計画は作りません。

```text
## 判定
- 結論: 直す / 直さない
- 根拠: 3章のどの段階で決まったか

## 直すもの
| 対象ファイル | 当てはまる基準（design-principles の章） | 内容 |
|---|---|---|

## 直さないもの
| 対象ファイル | 気になった点 | 直さない理由 |
|---|---|---|

## 影響
- 変わる振る舞い（無ければ「なし」）
- 直すテスト・文書
```

作業を終えたときは、実行したテスト（5.1 で実行したか）と結果、直した文書、直さなかったことを報告します。

## 6. してはいけないこと

- 2章の不変条件に反する変更
- 3章の判定を通らない構造の整理
- ジョブのモジュール同士で関数を共有する、ジョブの名前を実行基盤・ブラウザ境界に書く
- 1行のラッパーや、使う場所が1つしかない抽象を増やす
- 処理の順序を上から読めなくするだけの分割
- 判定ルールを Flow・ページスクリプト・連携ジョブに書く
- ページスクリプトに CSV の処理や業務の判定を書く。PowerShell に画面の探し方を書く
- テストの期待値を、実装に合わせて理由なく書き換える
- 本番の設定（`app/config/settings.psd1`）の値を、テストを通すために変える

## この文書を更新するとき

- 不変条件、判定の手順、変更の進め方、提案の形が変わったとき（不変条件を変えるときは設計判断の記録も追加する）
