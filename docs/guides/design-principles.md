# 設計の判断基準

コードを直す・整理するときに「どこに書くか」「分けるか」「抽象を残すか消すか」「似たコードをまとめるか」を判断するための基準です。個々の判断の経緯は [decisions](../decisions/README.md) に、守るべき規約と手順は [maintenance-rules.md](maintenance-rules.md) にあります。この文書は、その間にある「考え方」を書きます。

## 1. 優先順位

SOLID 原則や「高凝集・疎結合」は目的ではなく手段です。判断が衝突したら、次の順で優先します。

1. **誤操作をしない** — 取り違えたまま画面を操作しない。迷ったら止まる（[decisions/0001](../decisions/0001-dom-as-contract.md)）。
2. **本番の Windows PowerShell 5.1 で動く**（[decisions/0006](../decisions/0006-windows-powershell-5-1.md)）。
3. **テストで確かめられる** — 失敗・タイムアウトの経路まで、実時間・実ブラウザなしで確かめられる。
4. **読んで分かる** — 処理の順序が上から読める。名前が業務の言葉になっている。
5. **短い・抽象が少ない**。

「分けた方が SOLID らしい」は、3・4 が良くなるときにだけ理由になります。

## 2. 責務の置き場所（単一責任）

ファイルは「**何が変わったら、ここを直すか**」で分けています。同じ理由で変わるものは同じ場所に、別の理由で変わるものは別の場所に置きます。

| 変わる理由 | 置き場所 | 例 |
|---|---|---|
| 業務の判定ルール | 純粋関数（`Policy.ps1` など） | ON / OFF の条件、先月の範囲、ファイル名から区画コードを取り出す規則 |
| 処理の順序・止まる条件 | `Flow*.ps1` | 「CSV データエラーがあればブラウザに触れない」 |
| 外の世界（ファイル・時刻・ログ・ブラウザ・他のジョブ）の扱い | JobHost のサービス | ファイル操作の安全確認、ダウンロード完了の判定、スクロールのたどり方 |
| 画面の探し方・操作の仕方 | ページスクリプト（`app/browser`） | 「操作」ボタンをちょうど1つに決める、チェックボックスを押して状態を確かめる |
| 画面操作の業務名と、ページのメソッドの対応 | `Page.ps1` + `PageOperations.psd1` | `AssertExportScreen` → `CheckExportScreen`（Kind=Contract）→ `checkExportScreen` |
| 設定値の型と必須 | `Settings.ps1` | 整数か、1以上か、`{0}` を含むか |
| 出力の形（列と順番） | `Records.ps1` | 失敗一覧の列 |
| ジョブの結果の約束、ポートの形 | JobKit | `New-JobResult`、`Assert-PortShape` |

分けるべき合図:

- Flow の中に `if` の判定ルールが増えてきた → 判定を純粋関数に出し、Flow はその結果で分岐するだけにする。
- 純粋関数がポート（`$Ports`）や `Clock` を受け取り始めた → I/O を Flow 側へ戻す。純粋関数は値だけを受け取る。
- 1つのファイルを、2つの別々の理由で直すことが続いた → 理由ごとにファイルを分ける。

## 3. 依存の向き（依存性逆転）

依存は「実行基盤 → ジョブ」ではなく、**ジョブはポートの形にだけ依存し、実行基盤がその形を実装して渡す**向きです。モジュールの依存表は [ARCHITECTURE.md](../../ARCHITECTURE.md#1-構成要素と依存の向き) にあり、テストで固定しています。

| 守ること | 理由 | 検査するテスト |
|---|---|---|
| ジョブのモジュールは `JobKit` 以外を読み込まない | ジョブが実行基盤やブラウザ境界の作りに引きずられない | Architecture |
| Context に触れるのは合成ルート（`Ports.ps1`）とジョブコマンドだけ | ジョブが何に依存しているかを1か所で読める | Architecture |
| Flow・純粋関数はファイル・時刻・画面出力のコマンドを直接使わない | 偽のポートで全経路をテストできる | Architecture |
| PowerShell 側に DOM の探し方を書かない | 画面の変更がページスクリプトだけで閉じる | Architecture |
| PageBridge・JobHost・JobKit はジョブの名前を知らない | ジョブを足しても基盤を直さない | Architecture |

## 4. 残すべき抽象

薄く見えても、次の抽象は消しません。どれも「外の世界を隠す」「テストで差し替える」「取り違えを防ぐ」のどれかの役割を持っています。

| 抽象 | 残す理由 |
|---|---|
| ポートと `Assert-PortShape` | 本物と偽物の形のずれを実行前に検出する。ジョブの依存がポートの宣言だけで分かる |
| 各ジョブの `Ports.ps1` | 使うサービスとメンバーだけを宣言する場所。ジョブごとに必要なものが違う |
| ページポート（`Page.ps1`） | Flow を業務の名前で書けるようにし、操作カタログの名前や Kind を Flow から隠す |
| 操作カタログと Kind | ヘルパーが無いとき・呼び方を誤ったときの扱いを、操作ごとに書かずに一律で決める（[decisions/0004](../decisions/0004-operation-catalog-kinds.md)） |
| `Settings.ps1` | 設定の誤りを、画面に触れる前の開始時に全部見つける |
| 純粋関数（Policy・Plan・Reconciliation・Records） | 業務の規則を境界値まで表で確かめられる |
| JobHost の `Downloads` / `Lists` | ダウンロード完了の判定・スクロールのたどり方は誤りやすく、ジョブごとに書くとばらつく |
| 画面の部品（`app/browser/screens`） | 同じ画面を対象にするジョブの画面識別を1か所にする（ジョブごとに識別がずれない） |

## 5. 抽象を足す・消すときの条件

**足してよい**のは、次のどれかに当てはまるときです。

- ファイル・時刻・ブラウザ・プロセスなど、外の世界を隠す。
- テストで差し替える必要がある。
- 2か所以上が、**同じ理由で、必ず同時に変わる**処理を持っている。

**消すことを検討してよい**のは、次をすべて満たすときです。1つでも怪しければ残します。

1. 1行の受け渡しに近く、呼び出し側が知るべきことを減らしていない。
2. テストで差し替えに使っていない。
3. 変わる理由が呼び出し側と完全に同じ。
4. 消しても依存の向きが悪くならず、品質ゲートのテストに反しない。

## 6. 似たコードをまとめるか

基準は「**同じ理由で、必ず同時に変わるか**」です。見た目が似ていることは、まとめる理由になりません。

| 似ているもの | 判断 | 理由 |
|---|---|---|
| 各ジョブの `Ports.ps1` / `Settings.ps1` / ジョブコマンドの形 | まとめない | ジョブごとに使うポート・設定が違い、別々に変わる。共通化するとジョブ同士が依存する |
| 各ジョブのページポートの包み方 | まとめない | 業務の名前と操作の対応はジョブ固有 |
| 同じ画面の識別 | まとめる（screens の部品） | 同じ画面なら識別の基準は1つでなければならない |
| ダウンロード完了の判定、CSV の書き出し、安全なパスの確認 | まとめる（JobHost のサービス） | 規則が1つであるべきで、ばらつくと事故になる |
| 文字列・状態・要素の探し方の基本 | まとめる（pagekit） | どの画面でも同じ意味を持つ |

まとめるときは、共通部分を JobKit・JobHost・pagekit のどれに置くかを依存の向きで決めます。ジョブのモジュール同士で関数を共有することはしません。

## 7. 大きさの目安

**大きいファイル・長い関数をすぐ悪とみなしません。**

- Flow の関数は、処理の順序を上から読めることを優先します。順序の途中を別の関数に出すと、読む人は行き来することになります。80〜90行の Flow でも、1段ずつ `Invoke-LoggedStep` やポートの呼び出しが並んでいるなら分けません。
- 分けるのは、その部分が**業務上の名前を持つ**とき（例: 走査を `Flow.Scan.ps1` に、1区画の取引を `RecordTransaction.ps1` に）、または**単独でテストしたい**ときです。
- 短くするためだけの分割、1行のラッパー関数の追加はしません。

## 8. Windows PowerShell 5.1 ならではの判断

- PowerShell の `class` は使わず、scriptblock をメンバーに持つオブジェクトをポートにしています（モジュールの再読み込みや読み込み順の制約が多いため。[decisions/0002](../decisions/0002-ports-and-composition-root.md)）。
- `GetNewClosure()` の制約（非公開関数が見えない）があるため、サービスは使う関数を `Get-Command` で取り出して閉じ込めます（[powershell-primer.md](powershell-primer.md#getnewclosure--変数を閉じ込める)）。
- モジュールの読み込みは1段（ジョブ → JobKit）に保ちます。入れ子を深くすると、5.1 では読み込みの失敗の原因が分かりにくくなります。

## 9. 迷ったときの確認

- [ ] その変更は、1章の優先順位のどれを良くするか言えるか
- [ ] 変わる理由ごとに、直す場所が1か所になっているか
- [ ] 依存の向きを変えていないか（品質ゲートのテストが通るか）
- [ ] 消そうとしている抽象は、4章の表に載っていないか
- [ ] まとめようとしているコードは、本当に同じ理由で同時に変わるか
- [ ] 分けた結果、処理の順序が上から読めなくなっていないか
